ECHO-series diagnostics node: network placement & the TCP/8080 console

Article ID KB-ECHO-0731 Last updated 3 weeks ago Applies to ECHO-series (ECHO-70 … ECHO-79)

ECHO-series appliances ship with an on-device diagnostics console used by field engineers during commissioning and maintenance. This article describes where an ECHO node should sit on the customer network and how to handle its diagnostics interface before a production launch.

Before production: the legacy diagnostics console listens on TCP/8080. It is intended for the vendor-maintenance segment only. Disable or firewall it before go-live: it must not be reachable from public-facing DMZ services, and the appliance should never initiate sessions into ticketing or fare-validation networks.

Recommended placement

Install ECHO nodes on a dedicated vendor-maintenance segment, isolated from rider-facing systems. Diagnostics traffic should stay inside that segment; production data paths belong to the application network, not the maintenance appliance.

Ports the appliance exposes
  • 443/tcp: DeviceControl API (TLS). Used by the RailGate management platform.
  • 8080/tcp: Diagnostics console (HTTP). Maintenance only; restrict before production.
  • 9100/tcp: Device telemetry. Keep filtered from general network access.
Hardening the diagnostics console before launch
  1. Confirm the ECHO node is on the vendor-maintenance segment only.
  2. Disable the TCP/8080 console, or restrict it to the maintenance management host.
  3. Verify the appliance cannot route to ticketing / fare-validation addresses.
  4. Re-check firmware: report the running diagnostics build with your support case.
Segmentation notes

ECHO diagnostics nodes are maintenance devices. A node that can reach a ticketing address, or that answers on 8080 from a public DMZ, indicates a segmentation gap that should be corrected before the network carries rider traffic.
